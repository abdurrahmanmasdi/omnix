# Tenant isolation posture

Database row-level security is **inactive**. The retired `prisma/rls_defense_in_depth.sql` file was never part of the migration chain. The application currently uses verified membership context, service-level authorization, and a Prisma query extension to scope models with `organizationId`. `Message` is scoped through its conversation. This is application isolation, not a guarantee against arbitrary SQL from the runtime database role.

HTTP requests begin without a tenant. The JWT strategy installs `organizationId` only after signature, expiry, active user, and active membership validation. The webhook route uses a system context solely to receive a payload; its controller verifies the Meta signature before queueing it. The worker resolves the receiving channel from the provider account, drops absent or ambiguous matches, and proves the organization/conversation/channel relationship before mutation. Inbound and outbound jobs use stable IDs, tenant-scoped lookups, leases, and eligibility checks.

The legacy Nest gRPC tool listener and its unused `BookAppointment` and `UpdateLeadStatus` methods were removed. Python does not call these methods. The Python AI gRPC client still connects to the separate Python agent service.

The root Prisma client rejects raw SQL outside an explicit system context. The audited system raw SQL sites are the outbox claim, tenant-scoped embedding cleanup, and user-row locks in provisioning/invitation transactions. Transaction clients are not wrapped by that raw-SQL check, so any new transaction raw query requires review for explicit tenant predicates. System contexts are used for startup credential validation and cross-tenant schedulers; after loading a job they must re-enter a verified tenant context before patient mutations. System bypass is an application convention, not a database privilege boundary.

Disposable PostgreSQL acceptance tests in `test/tenant-isolation.e2e-spec.ts` create two organizations with overlapping role names and contact numbers. They exercise verified HTTP reads/writes, forged membership claims, direct Message reads/writes, root raw SQL denial, and signed/unsigned webhooks. `test/inbound-claim.e2e-spec.ts` additionally exercises cross-tenant job payloads and ambiguous provider-account routing. These tests do not prove database RLS, all nested relation shapes, or an independently compromised database connection. Before public signup, assess whether to add runtime-role RLS and dedicated tenant-aware transaction helpers.
